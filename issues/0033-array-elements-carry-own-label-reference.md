---
title: Follow-up to 0026 - give each array element its own label reference instead of scanning for one
status: open
labels: enhancement
---

Issue 0026 tried merging an array annotation into one spanning `DataArea` so `DataArea.labelFor` could compute `address - area.address` directly (O(1)) instead of `SubjectConfigurer`'s current per-element registration, which only labels the array's first element and makes `labelFor` walk backward through memory looking for the nearest same-kind labeled neighbor. It was rejected: a single spanning `Area` can't represent cases like `squirm.flo`'s `high_score_screen` (a label declared on one byte sitting inside a much bigger, unlabeled block, `top_line`) where code then reads `high_score_screen + 1` - a byte that was never part of any declared array at all. The backward scan resolves that correctly by crossing `.flo`-declared block boundaries; a spanning `Area` with its own fixed size can't.

Different angle this time: keep the current one-`DataArea`-per-element model (don't merge them - that's what broke 0026), but have the array-registration loop in `SubjectConfigurer.exitLine` give every element its own back-reference to the array's label and its own index, instead of leaving all but the first element's naming to be reconstructed later by a scan. Something like `DataArea` gaining `String arrayLabel` and `int indexInArray`, set once at creation time (`for (int i = 0; i < amount; i++) { ... new DataArea(..., name, i) ... }`), so `labelFor` becomes a direct `arrayLabel + " + $" + indexInArray` with no walk at all - and no dependency on whichever neighboring `Area` objects happen to still be there.

That second part is the main new motivation: it also fixes a problem the backward scan has with *partial* overwrites (relevant to issue 0031's placeholder-carving workflow). Today, if a sub-range in the middle of an array gets overwritten by a more specific annotation, the elements *before* the cut keep resolving fine, but anything after it that relies on `labelFor`'s backward scan has to walk back across the now-different `Area` sitting in the middle - fragile, and exactly the kind of "same kind, uninterrupted run" assumption issue 0026's own writeup flagged as fragile. If every element already carries its own `arrayLabel`/`indexInArray` baked in at creation, a carved-out middle section doesn't orphan anything: the untouched elements on either side still know their own name and offset regardless of what now sits between them.

Important distinction to carry into the design: this is *not* the same as setting `MemoryLocation.label` on every element. That field is also what `ResultWriter`/`AssemblyFileFormat.printAnnotation` checks to decide whether to print a `label:` line - setting it on every element would print a label line for every single byte of every array, which is not wanted. The back-reference belongs on the `Area`/`DataArea` object itself (consulted only by `labelFor`), not on `MemoryLocation.label` (consulted by the printer).

Done when: `DataArea.labelFor` no longer scans (`DataArea.sameKindAt`/the backward `while` loop in `DataArea.java` can go), array elements resolve their label via their own stored back-reference instead, and the squirm `high_score_screen + 1`-style case (label declared mid-block, code reads one byte past it, never separately declared) still resolves correctly - plus a new fixture covering the partial-overwrite case (carve a sub-range out of the middle of a labeled array; confirm the elements on both sides of the cut still resolve their own name/offset correctly). All existing fixtures (`blockoffset`, `squirm`, `zwark` especially) must still pass unchanged.
