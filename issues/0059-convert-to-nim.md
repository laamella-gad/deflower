Rewrite deflower in Nim. The main gain is a native single-file executable with no JVM, which settles [0019](0019-ship-as-single-executable.md) along the way, and fast start-up for the run-on-every-save loop ([0057](0057-watch-mode.md)). [0056](0056-help-flag.md), [0057](0057-watch-mode.md) and [0082](0082-mcp-server.md) wait for it, so their command line is written once, in Nim.

## Size

Checked on 2026-10-14:
- **deflower**: 5375 lines of Java in `src/main`, the grammar `Flo.g4` (mostly its format comment), 420 lines in `src/test` (`DeflowerTest` 329, the rest `PrintingTest`), and 123 snippet files (`short` 78, `large` 13, `init` 10, `find` 9, `strings` 7, `dump` 6). The largest classes are `Subject` (760), `ResultWriter` with `AssemblyFileFormat` (720), `Initializer` (578) and `FloReader` (488).
- **mpu6502**: 3774 lines. Deflower uses only part of it: the opcode table (`specification`: `Instruction`, `Opcode`, `AddressingMode`, about 720 lines), `ByteManipulation`, and the assembler (`SourceParser` with `Segment`, about 600 lines plus `assembler` helpers). The emulator core (`Mpu6502`, 1289 lines) is unused today; [0096](0096-run-the-code.md) would need it.
- **snippets-test-junit5-core**: 621 lines.
- Nim 2.2.10 and nimble are installed, and so is 64tass.

## What has to be replaced, not just translated

- **mpu6502** ([github.com/laamella-gad/Mpu6502](https://github.com/laamella-gad/Mpu6502), the user's own, checked out at `~/IdeaProjects/Mpu6502`). The opcode table decides how every byte decodes; an illegal opcode that comes out wrong changes the output. `SourceParser` is what `Verifier` and the snippets' round trip assemble with, so the Nim side needs an assembler too. Calling 64tass instead would bring back an outside dependency for `--verify`, and the snippets were checked against `SourceParser`, which differs from 64tass in places (e.g. `<label + 1`, issue [0074](0074-detect-address-setup-pattern.md)). Plan: convert mpu6502 to Nim in deflower's source tree but kept apart (see Decisions), the opcode table and the assembler first, the emulator core when [0096](0096-run-the-code.md) needs it.
- **ANTLR** (`Flo.g4` and the generated parser in `com.laamella.enflower`). ANTLR has no Nim target. Decided: [npeg](https://github.com/zevv/npeg) (see Decisions). The format description in `Flo.g4`'s header moves to a document of its own, e.g. `docs/flo-format.md`, which `CLAUDE.md` then points to.
- **Parse error messages.** 9 snippets expect ANTLR's wording: `line 2:8 mismatched input '*' expecting {'virtual', 'banked', ...}`, `missing NEWLINE at '$0900'`, `extraneous input 'foo' expecting NEWLINE`. npeg won't reproduce these, and shouldn't: they list grammar tokens, not what the user should write.
- **snippets-test** ([github.com/laamella-gad/snippets-test-junit5](https://github.com/laamella-gad/snippets-test-junit5), the user's own, checked out at `~/IdeaProjects/snippets-test-junit5`). It finds the snippet files, splits them into parts and expectations, compares, and rewrites missing expectations (`REGENERATE_EXPECTATIONS`). Deflower uses only the core (`SnippetTestFactory`, `SnippetFileFormat`, `BasePath`). Plan: convert the core to Nim on top of `unittest`, in deflower's source tree but kept apart (see Decisions). The snippet file format stays the same, so the 123 files move over unchanged.

  What runs each snippet is deflower's own: `DeflowerTest` (329 lines) gives the library one function per kind (`runShort`, `runLarge`, `runInit`, `runDump`, `runFind`, `runStrings`), which turns a snippet's input parts into its expected parts. They write the parts to a temporary directory, assemble `.prg` parts with `SourceParser`, run deflower and capture what it prints, hex-dump exported binaries, and check the round trip. These port along with deflower, on top of the Nim snippets-test.
- **Built-in includes.** `src/main/resources/deflower/c64*.flo` are read from the classpath. In Nim they are compiled into the executable (`staticRead`), so the single file still has them.
- **Build and scripts.** Maven, `pom.xml` and the `./deflower` script with its cached classpath go; a nimble package builds one executable. `CLAUDE.md`'s Commands section changes with it.

## What translates fairly directly

`Subject` and the memory model; the `Area` classes (a Nim object variant, or `ref object` with methods); `FlowAnalyser`; `AddressSetupFinder` and `SelfModificationFinder`; `CrossReferences`; `ResultWriter`/`AssemblyFileFormat`/`LineEmitter`; `MemoryMap`; `Verifier`; `PrgReader`, `MemoryImage` and the VICE snapshot reader (`vicevcf`, byte-level parsing); and the other modes (`Initializer`, `Dumper`, `Finder`, `TextFinder`).

Spots where Java behaviour leaks into the output and the port has to match it on purpose:
- iteration order of the maps and sets that feed the output (`TreeMap`, `LinkedHashSet`, `EnumMap`): Nim needs the same sorted or insertion order. No `HashMap` or `HashSet` order reaches the output (checked in step 3): they are only looked up, or walked to add labels named by their address;
- `String.format` and `Integer.toHexString` (case, padding);
- sort stability (`Comparator` chains, `Stream.sorted`);
- error and warning texts, word for word.

## Steps

1. **mpu6502 in Nim** (done): `nim/mpu6502/`, a nimble package (`nimble test` there) with `specification` (the opcode table: `opcodeName`, `addressingMode`, `illegal`, `cpuCycles`, `specialCycles` per opcode, and `instructionByNr`), `byte_manipulation`, `segment`, `assembler` and `source_parser` (`assemble(source, files)`). The emulator core isn't ported; [0096](0096-run-the-code.md) would need it. `tests/opcodes.txt` is the Java table as the Java code printed it, and a test checks all 256 opcodes against it. The Java tests are ported, `AssemblerTest` checking bytes instead of running the emulator, with more cases for the error messages. Values wrap as Java ints, the source is read as Unicode characters with Java's white space, letters and digits, and every error message is the Java one, `Long.parseLong`'s included: deflower prints them. Errors raise `AssemblerError`, or `SourceError` (with its `line`) for one in the source text. A cross-check assembled the snippets' sources and expected `.asm` files and the 13 large outputs, 169 files, with both: the same segments, or the same message. Deflower's round trip checks it again once deflower is ported.
2. **snippets-test core in Nim** (done): `nim/snippets_test/`, a nimble package (`nimble test` there) of one module, `snippets_test`, on top of `std/unittest`. `runSnippetTests(format, basePath, filter, testCase)` makes one unittest test per snippet file, named by its relative path, sorted; `snippetFileFormat` takes the six strings in the Java order, `fromPath`/`fromSourceDirectory`/`inSubDirectory` build the directory, `allFiles`/`filesWithExtension` filter, and `simpleTestCase`/`multiInputTestCase`/`multiOutputTestCase` wrap a proc. Reading, writing, splitting (`splitParts`, Java's `Split`) and the messages are the Java ones; an error's message becomes the actual output, except a `SnippetTestFailure` (a misused test case, a description without its end, a missing directory), which fails the test. `REGENERATE_EXPECTATIONS` is an environment variable now. A mismatch prints the expectations, the actual output and the first line that differs. The steps of one test (`executeSnippetTest`, giving passed, failed or generated) are public, so the tests cover them in a temporary directory, besides the ported `SplitTest`, `TestCaseFilenameFilterTest` and `SnippetTestFactoryTest` with `test1/tc1.txt` and `tc2.txt`. `cases/pietje.txt` belongs to the extension (`Snipsertions`), which isn't ported, nor is `BasePath`'s Maven and class-name paths. Deflower's 1.0 and the checked-out 1.1.0-SNAPSHOT differ only in comments and null annotations.
3. **Prepare in Java** (done): everything that changes snippet output, done before the port so the snippets stay the measure. Parse errors are now in deflower's own words: one `line N: expected <parts>, found <token>` per bad line, its first problem, with the parts named as in the format description (`FloReader.describe`; `short/invalid/syntax-errors.txt` shows them in most places), or `unexpected '~'` for a character no word holds. Where ANTLR only expects the end of an annotation line, having passed over optional parts that didn't fit, the parts that may still follow come from the line's fixed shape (`FloReader.remainingLineParts`); the npeg grammar has to give the same lists. No `HashMap` order reached the output, so nothing changed there.
4. **Port deflower** (done): `nim/src/`, the nimble package `deflower` in `nim/`, which builds the `deflower` executable (`nimble build`) and runs all 123 snippet files of `src/test/snippets/` in place, plus `acceptsLastLineWithoutNewline` (`nimble test`, `tests/test_snippets.nim`, with the runners of `DeflowerTest`; the large ones on a copy of `src/test/resources/`). All pass, the round trip included. The modules follow the Java classes: `flo_reader` (`FloReader` with its `AnnotationCollector`), `subject` (`Subject`, the areas, `MemoryLocation` and the small value types), `loaders` (`PrgReader`, `ViceSnapshotReader`, `MemoryImage`), `vicevcf`, `flow_analyser` (with `InlineData`), `finders` (`AddressSetupFinder`, `SelfModificationFinder`), `cross_references`, `result_writer` (`ResultWriter`, `AssemblyFileFormat`, `LineEmitter`), `memory_map`, `verifier`, `runner` (`SubjectConfigurer` and `Deflower.deflower`), `initializer`, `look` (`Dumper`, `Finder`, `TextFinder`, `Deflower.look`) and `printing`; `src/deflower.nim` is `Deflower.main`, with the same usage text and exit codes. The built-in includes are compiled in with `staticRead` from `src/main/resources/deflower/`. The `.flo` parser is two npeg stages: a lexer over the characters gives tokens (a word is a keyword, else a number if all digits, else a name), and a grammar over the token kinds parses one statement, a line's tokens up to its newline, with code blocks filling the statement. An error is the furthest token the grammar reached (`matchMax`), described with `expectedParts`/`remainingLineParts` as in Java; the first error of a line by column wins between the lexer and the grammar. Since each line is parsed on its own, an error never carries over onto the next line the way ANTLR's recovery could; no snippet has such a case. Java behaviour kept on purpose: `int` wrapping of a `dword`, `Integer.parseInt`'s messages in `--dump`/`--find`/`--strings`, `%x` of a negative number in `--init`, stable sorts. Memory past $ffff reads as 0 in the writer, where Java would throw.
5. **Switch over** (done): the Java sources and tests, `pom.xml` and `Flo.g4` are deleted, and the Nim project is lifted out of `nim/` to the root: `deflower.nimble`, `config.nims`, `src/`, `tests/`, with `mpu6502/` and `snippets_test/` as top-level directories next to them. The snippets moved to `tests/snippets/`, the test programs to `tests/resources/`, and the built-in includes to `src/deflower/includes/`, still compiled in with `staticRead`. The format description from `Flo.g4`'s header is `docs/flo-format.md`. `nimble build` writes `bin/deflower`; the `./deflower` script rebuilds it (`nim c -d:release`) when it is missing or a source is newer, then runs it, so it still works from anywhere. `CLAUDE.md` describes the Nim project, and the open issues name the Nim modules and the new paths. All 123 snippet files pass unchanged, and so do the tests in `mpu6502/` and `snippets_test/`.

Done when: a Nim build produces one executable that passes every snippet, `--verify` works without outside tools, the Java sources, `pom.xml` and grammar are gone, the `.flo` format is described in its own document, and `CLAUDE.md` describes the Nim project.

## Decisions

- **Side by side.** The Nim version is written next to the Java one. Both run on all snippets until the Nim one passes every one, then the Java code is deleted.
- **A straight port.** No output changes in the same step; open issues are fixed before or after the port. Output changes the port needs (parse errors) are made in Java first.
- **npeg replaces ANTLR.** [npeg](https://github.com/zevv/npeg) (MIT, by zevv, after Lua's LPeg; the most used Nim parsing library, 1.3.0 installed) turns a PEG grammar written in Nim into Nim procs at compile time, so it adds no run-time dependency to the single executable. The grammar stays a grammar, as `Flo.g4` is now, rather than hand-written code. Its code-block captures fill the `Annotation`s directly, so there is no generated parse tree to walk as `FloReader` does now. For errors it has `E"..."` atoms, which fail with a message of our own (`E"a label"` after a type), and `matchMax`, the furthest position reached; a quick try gave `a label at 6` for `$c000 * foo`. That fits deflower's own error wording (step 3). Others looked at: `std/pegs` (string-based patterns, no captures with code, weaker errors), nimly (LALR(1) lexer and parser generator, less used, nothing on error messages). The format description moves from `Flo.g4`'s header to its own document.
- **mpu6502 and snippets-test live in deflower's source tree, but apart.** Each is its own directory (e.g. `nim/mpu6502/` and `nim/snippets_test/` next to deflower's own `nim/src/`), with its own tests. They don't import deflower or each other, and hold nothing deflower-specific: deflower uses them only through their public procs, as it would a library. Deflower's snippet runners stay in deflower's tests. That way each can be split off into its own nimble package and repository later, by moving the directory, without changing its code.
- **No tracing.** [0077](0077-analysis-warnings-report.md) dropped it, so there is no `--verbose` to port: a run prints only warnings, errors, the files it writes and the verify report.
- **In a `nim/` directory of this repository.** It shares `src/test/snippets/` and `src/test/resources/` directly and keeps one history. `~/IdeaProjects/deflower_nim` (May 2026, one commit, 289 lines: a tokenizer for the grammar of then and a `CLAUDE.md` describing deflower as it was) is too little and too old to build on, and is left alone.
- **Deflower's own parse error messages, in Java first.** Step 3 rewrites the Java `FloReader`'s errors in deflower's own words, e.g. `line 2: expected a type or a label, found '*'`, so the 9 snippets change once, in Java, and the npeg grammar's `E"..."` messages then match them. That keeps "passes every snippet unchanged" exact.
- **Feature freeze.** No feature work on the Java code from the start of the port until the switch, so no change has to be made twice. Bug fixes that change output are made in Java and the snippets carry them over. They aren't frozen: that would leave known bugs in the output for the length of the port, and a fix shows up as a changed snippet, which the Nim port then has to match like any other.

## Closing note

Done on 2026-10-14. Deflower is a Nim project now: one native executable, `bin/deflower`, built by `nimble build` or by the `./deflower` script, which passes every snippet unchanged with `nimble test`. `--verify` assembles with the Nim mpu6502 in `mpu6502/`, so it needs no outside tool. The Java code, `pom.xml` and the grammar are gone, the `.flo` format is described in `docs/flo-format.md`, and `CLAUDE.md` describes the Nim project.
