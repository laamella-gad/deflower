## Purpose

Deflower semi-automatically disassembles 6502 binaries. The tool traces code automatically, following control flow from entry points. The user supplies the rest by hand: labels, and marked areas (data, bytes, words, code entries). The `.flo` file is where those annotations live, so the tool is a loop of: run, read the output, add annotations, run again.

Suggested way to use it: `./deflower --watch <file.flo>` re-runs the disassembler on every save of the `.flo` file, and the generated `out/<binary>.asm` updates as you go.

## Commands

`README.md` is the user manual: building, the command line, the whole `.flo` format and the output. Keep it up to date with every change a user can see. `./deflower --help` prints a summary of it, `src/deflower/help.txt`, compiled in; keep that in step too. No other user documentation, and no long doc comments in the code.

Nim project (Nim 2.2), one nimble package at the root, `deflower.nimble`, with no dependencies. `mpu6502/` (the 6502 opcode table and the 64tass-style assembler the verifier and the tests use) and `snippets_test/` (the snippet test runner on top of `std/unittest`, `runSnippetTests`) are nimble packages of their own, used from source through the paths in `config.nims`; they import nothing of deflower's.

- Build: `nimble build`, which writes `bin/deflower` (ignored by git).
- Regenerate the `.flo` parser: `nimble flo` builds lindeboom (the user's parser generator, sources in `LINDEBOOM_SRC`, default `../nim_parser_generator`) into `bin/lindeboom` and generates `src/deflower/flo/flo_lexer.nim`, `flo_parser.nim` and `lindeboom_runtime/` from `src/deflower/flo/flo.ldb` (`gen --standalone`). Never edit the generated files. `tests/test_flo_parser.nim` fails when they differ from a fresh generation (skipped without lindeboom's sources) or when `README.md`'s copy of the grammar differs.
- Run all tests: `nimble test`. The packages in `mpu6502/` and `snippets_test/` have their own: `nimble test` there.
- Run one snippet: `nim c -r tests/test_snippets.nim <file name>`, e.g. `terminator.txt`.
- Run the tool: `./deflower <file.flo>` from anywhere. The script rebuilds `bin/deflower` (`nim c -d:release`) when it is missing or a source is newer, then runs it. All paths are file system paths, and output goes to `out/` next to the `.flo` file (ignored by git). `runner.deflower(path, verify)` runs a `.flo` file from code, and `deflower.command(args)` the whole command line, returning the exit code.
- Help: `./deflower --help` (or `-h`) prints `help.txt` and exits 0; no or bad arguments print the usage lines to stderr and exit 2 (`tests/test_command.nim`).
- Keep running: `./deflower --watch [--verify] <file.flo>` (`watcher`) does one run, then another whenever the `.flo` file, a `.flo` file it includes from disk or a binary it loads changes, until interrupted. It polls the modification times every 200 ms and waits for them to settle. A run with errors in any of its `deflower` lines leaves all of `out/` as it was (`runner.run` with `keepOnError`). Each run ends with a status line: `12:03:41 ok, watching game.flo` (or `doesn't verify`, or `failed, out/ unchanged`).
- Verify a disassembly: `./deflower --verify <file.flo>`. After writing each `.asm`, `verifier.verify` reassembles it with mpu6502's assembler and prints `Verify out/<binary>.asm: N bytes emitted, N differ, N virtual, N gaps`, then `differ $addr expected $xx got $yy` lines (the first 10) and `gap $start-$end` lines (end exclusive, pastable into the `.flo` file). A gap is loaded memory no area covers; an included virtual area dropped as unused still counts as covered. The exit code is 1 when anything differs, there is a gap, or a run has errors. A disassembly is done when it verifies with 0 differ and 0 gaps.
- Start a disassembly: `./deflower --init <file>` takes a `.vsf` or `.prg` and writes a `.flo` skeleton for it next to it, `<file without extension>.flo` (`initializer`). It won't overwrite an existing `.flo` file (exit code 1). The facts come as `;` comments: for a snapshot the banking, CPU registers, stack, the IRQ/BRK/NMI vectors (and the hardware vectors while the KERNAL is out) marked ROM, RAM or untouched RAM, changed KERNAL vectors, video (VIC bank, mode, screen, charset or bitmap, sprites), interrupt sources, the BASIC program and its `SYS`, and a patched CHRGET; for a `.prg` the load range and the `SYS` of a BASIC stub. Then come the `deflower` line, `code` lines for the entries found (`snapshot_pc`, `irq`, `nmi`, ...; not in ROM, the zero page or untouched memory), the ranges at `$0400` and up that still hold VICE's power-on pattern (`untouched_xxxx`) or only zeroes (`unused_xxxx`) (`$00`/`$ff` bytes, ones a bit off next to them and lone random bytes in a long run; trimmed to exact `$00`/`$ff` at both ends; a run without a fair share of both `$00` and `$ff`, like a sparse sprite, only gives its long zero stretches as `unused`), and the includes that match the banking. The video and VIC interrupts are only read from x64sc's `VIC-II` module 1.3 (VICE 3.x); older snapshots say they're unknown.
- Look at the bytes: `./deflower --dump <file> <start>-<end>` takes a `.vsf` or `.prg` and prints the range (end exclusive, as in a `.flo` file, so a verify `gap` line can be pasted) as hex, 16 bytes a line from the start, then as PETSCII and as screen codes (`look.dump`). Both text columns read the bytes with the lower/upper character set and show every character with a printable counterpart (letters, digits, punctuation, `£↑←`, the shifted space; screen codes reversed or not), graphics and control codes as `.`. Memory the file doesn't load shows as `..`. `loaders.readMemoryImage` reads the file for `--dump`, `--find`, `--strings` and `--init`.
- Search the bytes: `./deflower --find <file> <pattern> [in <start>-<end>]` (`look.find`). One number above 255, or one hex number with 3 or 4 digits, is an address: found as a word (`addr`), as the address minus one (`rta`), and as a low and a high byte at the same index in two tables 2 to 256 bytes apart (`lo/hi`, with a neighbouring entry's high byte within 1; one line per low byte, the matching high bytes as ranges). Anything else is a byte sequence (`$a9 $00 $8d`). Each hit prints its address, kind and the 8 bytes from there.
- Find text: `./deflower --strings <file> [<start>-<end>] [min <n>]` (`look.strings`) lists the stretches that read as PETSCII (`ascii`) or screen codes (`screencode`), with `--dump`'s characters. A stretch has at least 6 characters besides spaces (or `min <n>`), at least half of them letters and half of them different, letters in one case apart from a capital at the start of a word; `@` and reversed screen codes don't count. Followed by `$00`/`$ff` it prints as `<start> <type>[until $xx]`, preceded by its length as `<start> <type>[lengthbyte]`, else as `<start>-<end> <type>`, then the text: pastable into a `.flo` file. These are only candidates.
- `look.look` runs `--dump`, `--find` and `--strings` for the command and the snippet tests.
- No linter or formatter is configured.

All snippet tests pass.

## Architecture

The pipeline is: **flow file → parse → memory image + annotations → code-flow analysis → assembly output**. The command is `src/deflower.nim`; everything else lives in `src/deflower/`.

- **Input.** A `.flo` file describes the disassembly. Its full, authoritative description is the `.flo` format section of `README.md`; read it before writing or editing `.flo` lines, and keep it up to date with the syntax. In short:
  - `deflower <file>` starts a run: it loads a `.vsf` VICE snapshot or a `.prg`, relative to the `.flo` file. Each run is independent and writes `out/<file without extension>.asm`.
  - An annotation line is `<address or start-end> [virtual] [<type>[<size>]] [<label>] [export <id>] [{]`, with the parts in exactly that order and each at most once. Anything else is a parse error.
    - The range end is exclusive.
    - Types are `screencode`, `ascii`, `byte`, `word`, `long` (24 bits), `dword`, `addr` (a 16-bit address, printed as `.addr` with its target's label), `rta` (an address minus one, as an `rts` dispatch table holds it, printed as `.rta` with the label of the address plus one, which is traced as code; `addReturnAddress`), `sbyte`/`sword`/`slong`/`sdword` (signed, printed as `.char`/`.sint`/`.lint`/`.dint`) and `code` (an entry point). `screencode`/`ascii` are text in Commodore screen codes/ASCII (64tass `"screen"`/`"none"`), printed as `.text`; nothing about text is guessed. A text array is a `.null` when sized `[until $00]` and a one-line `.ptext` when sized `[lengthbyte]` (the data area's `terminator`, `lengthByte`). A range with no type is a placeholder, which a later line may narrow without an area conflict. A single address with no type is only a label/comment and registers no area.
    - The size is a number or `*`/`+` over numbers (`byte[40*21]`, `byte[$af]`), or `until <n>`: up to and including the first element holding `n` (`ascii[until $ff]`), or `lengthbyte` (one-byte types only): a byte holding the number of elements after it. A size of 0 is an error.
    - A `code` line can take a parameter list and `noreturn`: `$2c75 code print_inline (ascii[until $ff] text)`. Each parameter is `<type>[<size>] [<name>]`, the data after every `jsr` to the routine. The flow analyser registers it at each call site (`registerInlineData`), prints the names as a comment after the `jsr` (`Subject.callComments`), and traces on after it; a `.flo` data line at the call site wins. `noreturn` stops the trace after the call (`Routine`, `Parameter`).
    - `<address> banked <label>` names a flow target in memory banked in over the RAM, like a KERNAL routine over the program's data (`MemoryLocation.banked`). `jsr`/`jmp`/branches and `rta` values print the name and aren't traced (`bankedTarget`), as do `.addr` values and an address setup's `#<`/`#>` when the RAM has no label there (`bankedValueName`); reads and writes keep the RAM's name. The KERNAL and BASIC entry points of the built-in `c64_kernal.flo`/`c64_basic.flo` are banked lines. The names print as defines at the top of the output (`printBankedDefines`), an included one only when used (`Subject.usedBanked`). Banked lines are applied first. An included banked name gives way to the file's own label of the same name at the same address and to its own code line; an own banked line next to an own code line is an error (`checkBankedCodeEntries`).
    - `<address> selfmod <label>` names the operand of the self-modified instruction at the address: the label, plus or minus the distance to the value the image holds (`Subject.selfModNames`/`selfModLabels`). On an instruction no traced code writes it is a warning.
    - The reserved words (including `until`, `lengthbyte`, `noreturn`, `banked` and `selfmod`) can't be labels.
    - `export <file>.bin` on a data line writes its bytes to `out/<file>.bin` and prints `.binary "<file>.bin"` in their place. `export <file>.prg` puts the region's start address in front as a load address, printed as `.binary "<file>.prg", 2`. The region is fixed data, even untyped (`ExportRegion`, the data area's `export`).
  - `include <file>` reads another `.flo` file's lines into the run: relative to the including file, else a built-in one from `src/deflower/includes/`, compiled into the executable (`c64.flo`, which includes `c64_zeropage.flo`, `c64_system.flo`, `c64_io.flo`, `c64_basic.flo` and `c64_kernal.flo`). Included lines are weak: the including file's own lines win wherever they overlap, in any order. Included virtual areas and labels on uncovered memory are only printed when an operand or `.addr` value refers to them.
  - A `<address> [virtual] {` line opens a block, closed by `}`: addresses inside are offsets from that address, and `virtual` applies to every line inside. Blocks don't nest; `flo_reader` resolves them, so nothing after parsing knows about them.
  - `;`/`#` comments sit on their own line and attach to the next annotation line.
- **`runner`** (`configure`) drives the two configuration phases.
  - **Parse:** `flo_reader.readFlo` turns the `.flo` file into one `DeflowerRun` per `deflower` line, each holding its `Annotation`s (one per line, plain values; `LineType` is the line's kind; `included` for a line from an included file). It reads nothing but `.flo` files and changes no memory. The parser lindeboom generated from `flo/flo.ldb` (an ANTLR 4-style grammar without code) reads it into a parse tree, and `build` turns each statement node into a `Statement`. Syntax errors abort with "Failed to parse", then one `line N: expected <parts>, found <token>` per bad line, for its first problem; the parser's formatter hook (`describe`) names the parts as `README.md` does.
  - **Apply:** for each run, `configure` creates a `Subject`, loads the image (`loaders.readViceSnapshot` or `readPrg`, picked by extension), and calls `Subject.annotate` for each annotation, the run's own ones first and the included ones after, so these only fill in what is still free. Data lines register one data area per element; `code` lines push an entry point onto `potentialCodeLocations`.
  - To add `.flo` syntax, change `flo/flo.ldb` and run `nimble flo`, then `build` and `describe` in `flo_reader`, `Annotation` and `annotate`, the format section of `README.md` (its grammar section too) and the summary in `src/deflower/help.txt`.
- **`subject`** holds the `Subject`:
  - the 64K `MemoryLocation`s (each location has the byte, an `Area` reference, a label and a comment);
  - the `potentialCodeLocations` stack and the output path;
  - the `errors` list. `registerArea` reports one area overwriting a different, non-placeholder one, and `runner.deflower` skips writing output for a subject with errors.
  - the `warnings` list (`warn`, `Warning`): suspect spots that don't stop the output, printed after the analysis as `warning: $addr: text`, sorted by address. They cover a flow into a non-virtual data area, into the middle of an instruction or into memory the image doesn't load (unless a `.flo` label names the target), a `jsr` that returns into data, an instruction that would run into another area or past the image, a jam, a data line on memory the image doesn't load, and an `untouched_`/`unused_` virtual range of the `.flo` file's own that an instruction's operand names, unless an included label names the target (`warnUsedSkeletonRanges`).
  - It also answers memory questions used by the output: run and array boundaries (`continuesRun`, `endOfRun`, `endOfArray`) and annotations (`isAnnotated`).
- **`flow_analyser`** (`analyseCodeFlows`) pops entry points and follows 6502 control flow using `mpu6502`'s instruction table.
  - It registers an instruction area for each decoded instruction, follows fall-through and branch/jump/JSR targets (including `JMP (indirect)` through the address it reads), and auto-labels targets (`lXXXX`, `dXXXX`, `aXXXX`).
  - Analysis stops at addresses already covered by a non-placeholder area, and won't decode an instruction whose bytes run into one. It also stops at memory the image didn't load (`MemoryLocation.loaded`): the target keeps its label, printed as a define. That is how it avoids loops and detects jumps into data. Each entry on the stack is a `CodeEntry`, which records the instruction the flow came from, so the warnings can name it. A target is pushed even when an area covers it, and the analyser warns there instead of decoding.
- **`finders`** looks through the decoded code after the tracing:
  - `findAddressSetups` finds address setups: four instructions in a row that store the two halves of a constant address, each an immediate `lda`/`ldx`/`ldy` and the matching store, into the two bytes of an `addr` (not a `word`, which is as often a number). It labels the built address like a data reference and records the immediates in `Subject.lowByteSetups`/`highByteSetups`.
  - `findSelfModifications`, run after it, finds self-modifying code: an instruction whose operand bytes another instruction writes or modifies (branches aside), recorded in `Subject.operandWriters`. Its operand prints as a number with `; operand set by <routine>` after it, makes no cross-reference or skeleton warning and keeps no included name, and the auto labels only it made are dropped. It also resolves the `selfmod` lines' labels, an error when there is none.
- **`Area`** (`akData` or `akInstruction`) is one data element or one instruction. Each address belongs to at most one area, and `registerArea` writes that link into the memory. Address ownership is the main signal the analyser uses, so an overlapping `.flo` declaration changes the output.
- **`runner.run`** runs the pipeline and returns an `Outcome`; `runner.deflower` wraps it for a single run. It first analyses every subject, which ends with dropping the unused included names (`dropUnusedIncludes`). Then it clears and recreates `<basePath>/out` once per `.flo` file (with `keepOnError`, only when no subject has errors), and for each subject without errors writes `out/<binary>.asm` from `result_writer.writeAssembly`. It also writes `out/<binary>.map` (`memory_map`: one line per code run, split at routine labels, per array and per gap, e.g. `$c007-$c009 word table`), and with verify on runs `verifier.verify`.
- **`result_writer`** walks 0x0000–0xFFFF (`ResultWriter`) and drives `AssemblyFileFormat`, which owns the layout and the per-type printing (64tass syntax, all lowercase except labels and comments):
  - `*=` origins at gaps;
  - blank-line separators and label placement inside data runs;
  - `.byte`/`.word`/`.long`/`.dword`/`.addr`/`.rta`/`.char`/`.sint`/`.lint`/`.dint` tables;
  - `.text` strings, with `.enc "screen"`/`"none"` switches by the text type, and `.null`/`.ptext` for arrays sized `[until $00]`/`[lengthbyte]`;
  - a blank line above a label only where the instruction before it ends the flow (`jmp`, `rts`, `rti`, `brk`), and after such an instruction even without a label;
  - `.virtual` blocks;
  - instructions with operands resolved to labels (`label + $offset` inside arrays), `@w` on absolute operands below `$100` so they don't reassemble as zero page, and `#<label`/`#>label` for an address setup's immediates when the address has a label of its own (no offset: 64tass and mpu6502 read `<label + 1` differently);
  - labels inside an array, a multi-byte element or an instruction printed as `label = $XXXX` defines after it, and labels on uncovered memory as defines in place;
  - cross-references above each label (`; called by:`, `jumped to by:`, `read by:`, `written by:`, `modified by:`), collected by `cross_references` from the decoded instructions and named by the nearest routine label before each one (auto labels of branch and `jmp` targets no `jsr` calls are local and skipped).

  `LineEmitter` is the low-level writer: lines, indentation, value columns and open quotes.
- **`vicevcf`** parses VICE snapshot files (`readVcf` → `Header` + `Module`s, `module` finds one by name and `ModuleKind`). `mkC64Mem` is the `C64MEM` module, which provides the 64K RAM image and the processor port. `mkMainCpu` holds the registers (module 1.1 with a 4-byte clock, 1.4 with an 8-byte one), `mkVicII` the 64 VIC registers (1.3 only) and `mkCia` the ports and interrupt mask of `CIA1`/`CIA2` (2.x). Other modules and versions are kept as `mkUnhandled`.
- **`printing`** has the hex formatting and the errors that stop a run (`StateError`, `ArgumentError`, `assertState`), and `printOut`/`printErr`, which the tests redirect.

Test-driven workflow:
- `tests/test_snippets.nim` runs the snippet files in `tests/snippets/`, one test case per `.txt` file, with `snippets_test`.
- A snippet file is an optional description between `>>>` and `<<<`, the input parts separated by `===` lines, a `^^^` line, the three expectations separated by `~~~` lines, and a closing `vvv` line. The expectations are what Deflower printed (stdout and stderr together, paths relative to the `.flo` file), the generated `.asm` (each under a `--- <name>` line when a `.flo` file has several runs; empty when the run had errors), and the other files in `out/`, each under `--- <name>`: the `.map` files as text and the exported binaries as hex dumps. The snippets run with verify on, so the printed part ends with each run's verify report.
- Short snippets (`short/`, purpose-built, one per feature or bug, error cases in `short/invalid/`):
  - The first input part is 64tass assembly, which mpu6502's assembler assembles into `test.prg`. Leave it empty when the `.flo` file fails before loading anything.
  - The second part is the `.flo` file, written as `test.flo`.
  - More parts are more files, each starting with a `; file: <name>` line. A `.prg` one is assembled, like the first part.
  - All files go into a temporary directory, and Deflower runs on `test.flo` there.
  - Round trip: every generated `.asm` must reassemble, with mpu6502's assembler, to the bytes of the `.prg` with its name. Bytes it leaves out aren't checked. A failure fails the test outright, without writing an expectation. A `; no round trip` line in the assembly skips this, for a snippet that shows verify reporting a difference (`short/verify.txt`).
- Large snippets (`large/`) are the real programs, whose binaries are too big for a snippet. The only input is a `.flo` path in `tests/resources/`, e.g. `zwark/zwark.flo`, with the `.flo` file and its binary in `tests/resources/<program>/`. They run on a temporary copy of `tests/resources/`.
- Init snippets (`init/`) name a `.vsf` or `.prg` in `tests/resources/` and expect the skeleton `--init` writes for it.
- Dump, find and strings snippets (`dump/`, `find/`, `strings/`) name a `.vsf` or `.prg` in `tests/resources/` and the flag's arguments, and expect what `--dump`, `--find` or `--strings` prints, or its error.
- A changed snippet file in a diff means the generated output changed; review it like any other test failure.
- To accept a new snippet or a deliberate output change, delete everything from the `^^^` line on and rerun the tests. Running with the environment variable `REGENERATE_EXPECTATIONS` set rewrites all of them. Either way, the test writes the actual output into the file and fails once, so you can review it before committing.
- The `.asm` of a short snippet can also be checked with 64tass: `64tass -q -b -o x.bin test.asm` must equal `test.prg` minus its 2-byte header.

Issues are tracked as `issues/NNNN-slug.md` (frontmatter `title`/`status`/`priority`/`labels`, priority `low`/`medium`/`high`); `issues/README.md` describes the format. `issues/open` lists the open ones by priority. To close one, set `status: done`, remove its `priority` and add a "## Closing note".

## Notes

- A run prints only warnings, errors, the files it writes and, with verify on, the verify report. There is no tracing.
- Numbers in `.flo` files are decimal, or hex with a `$` prefix.
